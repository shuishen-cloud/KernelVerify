## 三、关键发现

### 阶段一发现（2026-06-04）

1. **Nightly wheel 可用**：`torch-mlir` 有每日构建的预编译 wheel，无需源码编译。
2. **导出 API**：正确入口是 `torch_mlir.fx.export_and_import()`，不是 `torch_mlir.compile()`。
3. **工具分工**：系统 `mlir-opt` 不含 Torch 方言，需用 `torch-mlir-opt` 验证 Torch Dialect。
4. **优化效果**：`--linalg-fuse-elementwise-ops` 成功融合 add+relu 为单 kernel。
5. **Pass 反效果**：`--linalg-generalize-named-ops` 反而增加 op 数，最优组合是 `fuse-elementwise-ops + canonicalize + cse`。

### 阶段二发现（2026-07-10）

6. **GPT-2 零干预导出**：GELU/LayerNorm 等特殊算子被默认分解表自动处理。
7. **大模型优化更显著**：GPT-2 linalg ops 降低 58.5%，远超简单模型 25.8%。
8. **规模递增效应**：模型越大、融合机会越多、优化越显著。

### Phase 3 发现（2026-07-13+）

9. **Linalg→GPU 全链路打通**：5 步 pipeline (bufferize→parallel-loops→gpu-map→gpu-convert→kernel-outline)，GPT-2 产生 832 GPU kernel。
10. **FX 图操作**：PyTorch 提供三层图操作入口 — FX Graph (Python)、MLIR Pass (C++)、IREE Pipeline (Python)。FX Graph 最易上手，`prog.graph_module.graph` 直接增删改 node。
11. **Pass Plugin API**：独立 Pass 编译为 `.so`，`mlirGetPassPluginInfo()` 入口点，通过 `--load-pass-plugin` 加载。注意 `torch-mlir-opt` 不支持插件，需用系统 `mlir-opt`。
12. **两种推理引擎**：编译器路线 (IREE/TensorRT) 优化单个 kernel，服务层路线 (vLLM/SGLang) 优化请求调度。项目聚焦编译器路线。
13. **模拟新后端模式**：融合 Pass (识别 pattern → 自定义 op) + 展开 Pass (自定义 op → 标准 op)，在现有硬件上验证正确性和优化效果。
14. **计算图可视化**：FxGraphDrawer + Graphviz DOT → SVG/PNG，直观展示节点和边的拓扑结构。
15. **pip 26.x 与 Python 3.10 不兼容**：需降级 `pip<25`。
16. **GPT-2 是补全模型非聊天模型**：需 Instruct 模型（如 Qwen2-1.5B-Instruct）才能对话。

## 四、技术架构

### 4.1 整体链路

```
PyTorch 模型
  → torch.export.export()           # 导出为 ExportedProgram (FX Graph)
  → prog.run_decompositions()       # ATen op 分解
  → FxImporter                     # FX → Torch Dialect MLIR
  → torch-mlir-opt                 # Torch Dialect → Linalg/SCF/Arith
  → mlir-opt                       # Linalg 层优化 (fuse/canonicalize/cse)
  → 优化后的 MLIR
```

### 4.2 计算图操作的三层入口

```
① FX Graph 层 (Python)  →  prog.graph_module.graph  →  增删改 node
② MLIR Pass 层 (C++)    →  --load-pass-plugin       →  W10/W12 已实践
③ IREE Pipeline (Python)→  iree.compiler.compile_str →  自定义 pass 编排
```

### 4.3 Phase 3 Linalg → GPU 全链路

```
Linalg IR
  → --bufferize                        # tensor → memref
  → --convert-linalg-to-parallel-loops # linalg → scf.parallel
  → --gpu-map-parallel-loops           # scf.parallel → gpu.launch
  → --convert-parallel-loops-to-gpu    # 生成 gpu 操作
  → --gpu-kernel-outlining             # 提取为独立 kernel
  → GPU Dialect (gpu.launch_func @kernel)
```

### 4.4 推理引擎选型

```
编译器路线 (本项目)            服务层路线
IREE / TensorRT              vLLM / SGLang
  优化: matmul 怎么最快         优化: 1000 个请求怎么排队
  kernel 由编译器生成            kernel 由 cuBLAS 提供
  多层 IR lowering              无 IR, 直接调度 PyTorch op
```

## 五、难点分析

### 困难 1：Torch MLIR 导出路径选择
- **问题**：torch_mlir 提供两条路径：基于 TorchScript（旧，`torch.jit.script/trace`）和基于 `torch.export`（新，FX Graph）。后者对 Python 的动态特性支持有限。
- **方案**：
  - 阶段一优先使用 `torch.jit.trace`（稳定，易于调试），模型简单不涉及动态控制流。
  - 阶段二 GPT-2 使用 `torch.export`（标准导出路径），若失败则回退到 TorchScript。
- **验证**：对比两种路径导出的 MLIR 文本结构完整性。

### 困难 2：MLIR Lowering Pass Pipeline 构建
- **问题**：Torch Dialect → Linalg 的下沉链路长，依赖多个 pass，顺序错误会导致失败。
- **方案**：参考 torch-mlir 自带的 `RefBackend` pipeline，简化关键路径：
  `torch-backend-to-linalg-on-tensors-backend-pipeline` → canonicalize → cse
- **验证**：输入手写 Torch dialect MLIR，逐 pass 运行确认不报错。

### 困难 3：优化效果量化
- **问题**：MLIR 生成后如何判断优化有效？
- **方案**：
  - 统计关键 op 数量（如 linalg.matmul → linalg.generic，scf.for 融合）
  - 对比优化前后 IR 的 op 数量、内存分配次数
  - 使用 `mlir-opt --mlir-print-ir-before-all --mlir-print-ir-after-all` 追踪变更

### 困难 4：GPT-2 模型 IR 规模过大
- **问题**：GPT-2 生成的 MLIR 文件可能数千行，阅读/调试困难。
- **方案**：使用 function-by-function 切分，只聚焦 attention 和 FFN 子图。

```bash
torch-mlir-opt --torch-backend-to-linalg-on-tensors-backend-pipeline test_matmul.mlir

mlir-opt --linalg-fuse-elementwise-ops --cse --canonicalize test_matmul_lowered.mlir
```

### 10.5 设计讨论：Triton kernel 如何融入 GPT-2？（2026-07-29）

**问题**：W14 写的 GELU/LayerNorm Triton kernel 如何在完整的 GPT-2 模型中运行？能否做 FX 图融合？

**分析**：

| 方法 | 可行性 | 问题 |
|------|:---:|------|
| `torch.fx.symbolic_trace(GPT2Model)` | ❌ | GPT-2 有动态控制流（attention/causal mask），symbolic_trace 失败 |
| `torch.export.export(GPT2Model)` | ⚠️ | 可导出但图是静态的（控制流展开/形状固定），改图后难以塞回原模型 |
| `torch.compile` + custom Triton backend | ⚠️ | 太重，需注册完整后端，学习成本高 |

**决策：模块级替换 (Model Surgery)**

不 trace 全模型，直接替换 GPT-2 内部模块：

```python
model = GPT2Model.from_pretrained("gpt2")
for block in model.h:
    block.mlp.act = TritonGELU()  # nn.Module 包装的 Triton kernel
```

理由：
- GPT-2 的结构和权重完全不变
- 只有激活函数/LayerNorm 的计算被 Triton kernel 替换
- 可以直接跑完整推理 + 产生有效端到端 profiling 数据
- 难度低（⭐），效果可测

**影响 W14 产出**：
- `scripts/fx_fuse_kernels.py` → 改为 `scripts/patch_gpt2_triton.py`（模块替换 + 端到端对比）
- 表F 仍然有效：原始 GPT-2 vs 各个 Triton 模块替换版本

**预期端到端收益**（基于表A profiling 数据）：
```
GPT-2 端到端 (1×128): ~40ms
  + GELU Triton fused:  ~39.3ms (-1.7%)
  + LayerNorm Triton:    ~39.0ms (-0.2%)
  + 两者叠加:             ~38.3ms (-1.9%)
```
> GEMM 占 75% GPU 时间且 cuBLAS 已极致优化，端到端收益天然受限。W14 的核心价值在于建立"profiling 依据 → 手动优化 → 对比验证"的方法链路，而非追求绝对加速数字。
