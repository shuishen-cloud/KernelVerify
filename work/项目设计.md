## 三、关键发现

### 阶段一发现（2026-06-04）

1. **Nightly wheel 可用**：`torch-mlir` 有每日构建的预编译 wheel，无需源码编译。
2. **导出 API**：正确入口是 `torch_mlir.fx.export_and_import()`，不是 `torch_mlir.compile()`。
3. **工具分工**：系统 `mlir-opt` 不含 Torch 方言，需用 `torch-mlir-opt` 验证 Torch Dialect。
4. **优化效果**：`--linalg-fuse-elementwise-ops` 成功融合 add+relu 为单 kernel。
5. **Pass 反效果**：`--linalg-generalize-named-ops` 反而增加 op 数，最优组合是 `fuse-elementwise-ops + canonicalize + cse`。

### 阶段二发现（2026-07-10）

6. **GPT-2 零干预导出**：GELU/LayerNorm 等特殊算子被默认分解表自动处理。
7. **大模型优化更显著**：GPT-2 linalg ops 降低 58.5%，远超简单模型 25.8%。
8. **规模递增效应**：模型越大、融合机会越多、优化越显著。

### Phase 3 发现（2026-07-13+）

9. **Linalg→GPU 全链路打通**：5 步 pipeline (bufferize→parallel-loops→gpu-map→gpu-convert→kernel-outline)，GPT-2 产生 832 GPU kernel。
10. **FX 图操作**：PyTorch 提供三层图操作入口 — FX Graph (Python)、MLIR Pass (C++)、IREE Pipeline (Python)。FX Graph 最易上手，`prog.graph_module.graph` 直接增删改 node。
11. **Pass Plugin API**：独立 Pass 编译为 `.so`，`mlirGetPassPluginInfo()` 入口点，通过 `--load-pass-plugin` 加载。注意 `torch-mlir-opt` 不支持插件，需用系统 `mlir-opt`。
12. **两种推理引擎**：编译器路线 (IREE/TensorRT) 优化单个 kernel，服务层路线 (vLLM/SGLang) 优化请求调度。项目聚焦编译器路线。
13. **模拟新后端模式**：融合 Pass (识别 pattern → 自定义 op) + 展开 Pass (自定义 op → 标准 op)，在现有硬件上验证正确性和优化效果。
14. **计算图可视化**：FxGraphDrawer + Graphviz DOT → SVG/PNG，直观展示节点和边的拓扑结构。
15. **pip 26.x 与 Python 3.10 不兼容**：需降级 `pip<25`。
16. **GPT-2 是补全模型非聊天模型**：需 Instruct 模型（如 Qwen2-1.5B-Instruct）才能对话。

### Phase 5 发现（2026-09-13+）

1. **Tiling 是性能数据可解释的前提**：无 tiling 时 GPU kernel 是 `block=(1,1,1)`、一个线程跑完全部，
   测到的是"最差实现"的耗时 —— 既无法做 roofline 判断，也掩蔽了其它优化的效果。这就是"因果倒置"的本意。
2. **Tiling / Layout / Mapping 是三件事**：Tiling = 分块（迭代空间切分）；Layout = 内存排布；
   Mapping = 哪块交给哪个 block/thread。三者需协同，但概念不同。
3. **Tiling ≠ 只切 K 维**：切哪些维是策略选择。对 matmul，M/N 管**并行**、K 管**复用**；
   **只切 M/N 不切 K 反而变慢**（0.96x）。
4. **K 切分带来可测收益**：朴素循环后端下 512³，tile 16~32 最优（**1.46x**），
   曲线呈典型 cache-blocking 形状（太小被循环开销吃掉、太大放不进缓存）。
5. **度量后端不能自带优化**：IREE 自身会 tiling/vectorize/并行化，喂预 tiled IR 会被"打断"，
   测得慢 9~1000x —— **要度量 tiling 必须用不做 tiling 的后端**（`mlir-runner` + `--convert-linalg-to-loops`）。
6. **张量层 tiling 会引入真实数据搬运**：`tile_using_for` 产 `insert_slice` → bufferize 后成 `memref.copy`。
   这说明 tiling 的收益落点在 **promotion**（把面板提升到 shared memory / 寄存器、消除该拷贝）。

## 四、技术架构

### 4.1 整体链路

```
PyTorch 模型
  → torch.export.export()           # 导出为 ExportedProgram (FX Graph)
  → prog.run_decompositions()       # ATen op 分解
  → FxImporter                     # FX → Torch Dialect MLIR
  → torch-mlir-opt                 # Torch Dialect → Linalg/SCF/Arith
  → mlir-opt                       # Linalg 层优化 (fuse/canonicalize/cse)
  → 优化后的 MLIR
```

### 4.2 计算图操作的三层入口

```
① FX Graph 层 (Python)  →  prog.graph_module.graph  →  增删改 node
② MLIR Pass 层 (C++)    →  --load-pass-plugin       →  W10/W12 已实践
③ IREE Pipeline (Python)→  iree.compiler.compile_str →  自定义 pass 编排
```

### 4.3 Phase 3 Linalg → GPU 全链路

```
Linalg IR
  → --bufferize                        # tensor → memref
  → --convert-linalg-to-parallel-loops # linalg → scf.parallel
  → --gpu-map-parallel-loops           # scf.parallel → gpu.launch
  → --convert-parallel-loops-to-gpu    # 生成 gpu 操作
  → --gpu-kernel-outlining             # 提取为独立 kernel
  → GPU Dialect (gpu.launch_func @kernel)
```

### 4.4 推理引擎选型

```
编译器路线 (本项目)            服务层路线
IREE / TensorRT              vLLM / SGLang
  优化: matmul 怎么最快         优化: 1000 个请求怎么排队
  kernel 由编译器生成            kernel 由 cuBLAS 提供
  多层 IR lowering              无 IR, 直接调度 PyTorch op
```

## 五、难点分析

### 困难 1：Torch MLIR 导出路径选择
- **问题**：torch_mlir 提供两条路径：基于 TorchScript（旧，`torch.jit.script/trace`）和基于 `torch.export`（新，FX Graph）。后者对 Python 的动态特性支持有限。
- **方案**：
  - 阶段一优先使用 `torch.jit.trace`（稳定，易于调试），模型简单不涉及动态控制流。
  - 阶段二 GPT-2 使用 `torch.export`（标准导出路径），若失败则回退到 TorchScript。
- **验证**：对比两种路径导出的 MLIR 文本结构完整性。

### 困难 2：MLIR Lowering Pass Pipeline 构建
- **问题**：Torch Dialect → Linalg 的下沉链路长，依赖多个 pass，顺序错误会导致失败。
- **方案**：参考 torch-mlir 自带的 `RefBackend` pipeline，简化关键路径：
  `torch-backend-to-linalg-on-tensors-backend-pipeline` → canonicalize → cse
- **验证**：输入手写 Torch dialect MLIR，逐 pass 运行确认不报错。

### 困难 3：优化效果量化
- **问题**：MLIR 生成后如何判断优化有效？
- **方案**：
  - 统计关键 op 数量（如 linalg.matmul → linalg.generic，scf.for 融合）
  - 对比优化前后 IR 的 op 数量、内存分配次数
  - 使用 `mlir-opt --mlir-print-ir-before-all --mlir-print-ir-after-all` 追踪变更

### 困难 4：GPT-2 模型 IR 规模过大
- **问题**：GPT-2 生成的 MLIR 文件可能数千行，阅读/调试困难。
- **方案**：使用 function-by-function 切分，只聚焦 attention 和 FFN 子图。

### 10.2 Profiling + 分析四层架构


### 10.3 算子与计算图分析（核心方法论）

**目标**：在写任何优化代码之前，先用数据流分析回答三个问题：
1. 这个 op 的输入来自哪个 op？（producer）
2. 这个 op 的输出被几个 op 消费？（consumer count）
3. 整个链是否可以安全融合？（无多 consumer、无跨库边界）

**工具**：`scripts/analyze_dataflow.py`

**方法**：
```python
prog = torch.export.export(model, inputs)
for node in prog.graph_module.graph.nodes:
    op_type = classify_op(node.target)      # MATMUL/ELEMENTWISE/REDUCTION/VIEW
    shape   = node.meta['val'].shape        # tensor shape
    consumers = list(node.users)             # 下游 op 列表
```

**融合安全性判断规则**：

| 条件 | 检查 | 不满足时 |
|------|------|------|
| 单 consumer | `len(list(op.users)) == 1` | 融合会破坏其他 consumer 的输入 |
| 同类型链 | 全为 ELEMENTWISE | MATMUL(cuBLAS) 不可跨越融合 |
| 单 producer | 输入只来自一个 op | 多 producer 导致依赖复杂 |
| 无跨库边界 | 不跨越 cuBLAS/aten 库调用 | 库内部实现不可控 |

**产出**：
- `benchmarks/tables/table_c_subgraph_ops.csv`：每个 op 的类型/shape/consumers
- `benchmarks/tables/table_c_fusion_chains.csv`：可融合的 elementwise 链
- 融合冲突点清单（多 consumer、跨库边界）

**在优化循环中的位置**：
```
Profiling (表A/B) → 数据流分析 (analyze_dataflow.py) → 确定可融 → 写Triton kernel → 模块替换 → 表D/F
                     ↑
                    这是 W14 教训：跳过了这一步，
                    导致写了 add+gelu 融合但发现 GPT-2 中无此 pattern
```

### 10.4 优化循环（完整版）

```
① Profiling (表A/B)
   └→ 回答"哪个 op 最耗时？"

② 数据流分析
   └→ 回答"producer→consumer 链是什么？有几个 consumer？可以安全融合吗？"
   └→ 工具: torch.export + graph node 遍历

   └→ 只有 ② 确认单 consumer、无跨库调用后才进入 ③

④ 写 Triton kernel → benchmark (表D/E)
   └→ 独立 benchmark 验证单 kernel 性能

⑤ 模块替换 + 端到端 (表F)
   └→ 只在数据流分析确认可行后才嵌入 GPT-2

⑥ 三段式记录：依据（①②）→ 动作（④⑤）→ 结果（表D/F）
```

每个优化遵循三段式记录：**依据（来自哪张表 + 数据流分析）→ 动作（什么优化）→ 结果（before/after 数据）**

### 10.6 设计讨论：Triton kernel 如何融入 GPT-2？（2026-07-29）

**问题**：W14 写的 GELU/LayerNorm Triton kernel 如何在完整的 GPT-2 模型中运行？能否做 FX 图融合？

**分析**：

| 方法 | 可行性 | 问题 |
|------|:---:|------|
| `torch.fx.symbolic_trace(GPT2Model)` | ❌ | GPT-2 有动态控制流（attention/causal mask），symbolic_trace 失败 |
| `torch.export.export(GPT2Model)` | ⚠️ | 可导出但图是静态的（控制流展开/形状固定），改图后难以塞回原模型 |
| `torch.compile` + custom Triton backend | ⚠️ | 太重，需注册完整后端，学习成本高 |

**决策：模块级替换 (Model Surgery)**

不 trace 全模型，直接替换 GPT-2 内部模块：

```python
model = GPT2Model.from_pretrained("gpt2")
for block in model.h:
    block.mlp.act = TritonGELU()  # nn.Module 包装的 Triton kernel
```

理由：
- GPT-2 的结构和权重完全不变
- 只有激活函数/LayerNorm 的计算被 Triton kernel 替换
- 可以直接跑完整推理 + 产生有效端到端 profiling 数据
- 难度低（⭐），效果可测

**影响 W14 产出**：
- `scripts/fx_fuse_kernels.py` → 改为 `scripts/patch_gpt2_triton.py`（模块替换 + 端到端对比）
- 表F 仍然有效：原始 GPT-2 vs 各个 Triton 模块替换版本

**预期端到端收益**（基于表A profiling 数据）：
```
GPT-2 端到端 (1×128): ~40ms
  + GELU Triton fused:  ~39.3ms (-1.7%)
  + LayerNorm Triton:    ~39.0ms (-0.2%)
  + 两者叠加:             ~38.3ms (-1.9%)
```
> GEMM 占 75% GPU 时间且 cuBLAS 已极致优化，端到端收益天然受限。W14 的核心价值在于建立"profiling 依据 → 手动优化 → 对比验证"的方法链路，而非追求绝对加速数字。

### 10.7 数据流分析：融合安全性的前置条件（2026-07-29）

**教训**：W14 开发中跳过了数据流分析直接写代码，导致后续发现 add+gelu 和 add+LN 融合**无法嵌入 GPT-2**（因为实际数据流中不存在独立的 add→gelu 链）。

**正确流程**：编 Triton kernel 之前，必须先用 `torch.export` 导出目标子图，遍历 graph.nodes，确认：

```
融合安全性判断：
1. 单 consumer？   len(list(op.users)) == 1     → ✅ 可融合
2. 同类型？       无跨库调用（cuBLAS不可融）     → ✅
3. 形状兼容？     producer/consumer shape 一致   → ✅
4. 无副作用？    不破坏其他 consumer 行为        → ✅
```

**GPT-2 实际数据流发现**：

| 候选融合 | 数据流事实 | 结论 |
|------|------|:---:|
| `add → gelu` | GPT-2 中 bias add 在 addmm 内部，无独立 add | ❌ 在 GPT-2 中不存在此 pattern |
| `add → LayerNorm` | residual add 有 2 个 consumer（LN + 下游残差） | ❌ 融合会破坏残差路径 |
| `GELU 内部 chain` | 单 producer 单 consumer，纯 elementwise | ✅ 安全融合 |
| `Attention mul→add→softmax` | 单 consumer 链，但跨 bmm(cuBLAS) 边界 | ⚠️ 超出当前能力范围 |

**为什么 GELU Triton 仍然有 1.08x 端到端提升？**

PyTorch 的 GPT-2 GELU 不是单个 cuBLAS 调用，而是被 torch.export 分解为 8 个 elementwise kernel：

```
PyTorch: mul → pow → add → mul → tanh → mul → add → mul
         (8 kernel launch + 7 个中间 tensor 显存读写)

Triton:  load → compute_all_in_registers → store
         (1 kernel launch + 0 中间 tensor)
```

每个 kernel launch ~5μs + 中间 tensor 显存读写（1×8×3072 floats × 7 次 ≈ 688KB 额外显存流量）。12 层 × 每次 GELU 的 8→1 kernel 节省，累积起来 = **1.08x 端到端**。

> 加速不是因为"Triton 比 cuBLAS 快"，而是因为**消灭了 kernel 碎片和中间 tensor 显存流量**。

详见 `benchmarks/analysis/w14_dataflow_analysis.md`。

### 11.1 验证阶梯 L1~L4

| 层 | 验证什么 | 判据 | 现状 |
|:--:|----------|------|:--:|
| L1 | 结构：tiling 是否生效 | 出现 `scf.for` 嵌套 + tile 形状的 `linalg.matmul` + `extract/insert_slice` | ✅ |

| L3 | 映射：GPU 结构是否改变 | `gpu.func` 的 `known_block_size` / `threads in (...)` 不再恒为 `(1,1,1)` | ✅（含已知边界）|
| L4 | 性能：实测 | 相对耗时 | ❌ 需 NVPTX |

### 11.2 度量后端的选择（关键方法论）

> **原则：要度量某个优化，后端必须不做那个优化。**

| 后端 | 适用 | 实测结论 |
|------|------|------|
| IREE `llvm-cpu` | 生产栈对照 | ❌ 自身会 tiling/vectorize/并行化，预 tiled IR 被"打断"，测得慢 9~1000x |
| `mlir-runner` + `--convert-linalg-to-loops` | **度量 tiling 本身** | ✅ 朴素循环、无自动 tiling，tiling 的效果被隔离出来 |

### 11.3 CPU 代理指标的边界

- **能验证**：数值正确性、tile 形状/大小对缓存复用的影响
- **不能验证**：shared memory promotion、occupancy、并行度 —— GPU 独有机制，只能等 NVPTX
- **不可外推**：CPU 上的收益比例 ≠ GPU 上的收益比例

### 11.4 度量框架

`scripts/verify_tiling.py`：变体化（内置变体 / `--tiles` 自定义）+ 双后端 + 数值校验 + 计时 + CSV 落盘。
`--backend runner`（默认）用于度量，`--backend iree` 保留作生产栈对照。
