# 开发经验

> 本文档总结在 PyTorch → MLIR 优化加速验证项目中积累的开发流程、方法论和教训。可作为后续类似项目的参考。

## 一、文档驱动开发

### 1.1 核心原则

**先写文档，再开发，再跟踪。禁止跳过文档直接写代码。**

代码会过时，文档是真相。在动手写任何代码之前，先在 `work/` 目录的三份文档中完成定义和设计。

### 1.2 三份文档体系

```
work/
├── 工作划分.md     ← 定义"要做什么"（任务描述、产出、优先级、难点）
├── 进度管理.md     ← 追踪"做了什么"（状态表、异常记录、时间）
└── 项目设计.md     ← 记录"为什么这样做"（架构、方法论、技术决策、讨论）
```

| 文档 | 角色 | 更新时机 | 读者 |
|------|------|------|------|
| `工作划分.md` | 任务定义 | 开始新 W 任务前 | 开发者（知道具体要产出什么） |
| `进度管理.md` | 状态追踪 | 任务状态变更时 | 管理者（知道进度和阻塞） |
| `项目设计.md` | 知识沉淀 | 方法论变更 / 讨论发生时 | 未来的自己（知道当时为什么这样决策） |

### 1.3 五步执行流程

```
1. 写文档   →  三份文档更新到位，git commit "docs: ..."
2. 讨论     →  编码前提出问题，结论写入项目设计.md
3. 开发     →  严格按工作划分.md 产出清单编码
4. 跟踪     →  状态更新、异常记录、关键发现追加
5. 提交     →  git commit "feat(W{n}): ..."
```

### 1.4 为什么这个流程有效

- **避免盲目开发**：先写产出清单，防止跑偏
- **决策可追溯**：几个月后回头看项目设计.md，知道当时为什么那样选
- **异常不丢失**：进度管理.md 的异常记录是宝贵的教训库
- **文档和代码一致**：文档变更和代码变更分开 commit，log 清晰

## 二、阶段化管理

### 2.1 W 任务编号体系

每个任务用 `W{n}` 编号，按执行顺序递增：

```
W0~W8   阶段一+二：MLIR Lowering 全链路验证
W9~W12  阶段三：Linalg 层聚焦 (GPU / Pass / Kernel)
W13~W15 阶段四：PyTorch 工具链 Kernel 优化
```

每个 W 任务包含：描述、输入、产出（具体文件路径）、难点、优先级（P0/P1/P2/P3）。

### 2.2 产出清单化

每个 W 任务的产出必须是**具体的文件路径列表**，不允许模糊描述：

```
✅ "产出：scripts/profile_gpt2_torch.py → benchmarks/tables/table_a_op_timing.csv"
❌ "产出：profiling 相关脚本"
```

### 2.3 进度状态机

```
⏳ (未开始) → 🚧 (进行中) → ✅ (已完成)
                            → ❌ (阻塞/放弃)
```

每行进度表包含：任务 ID、描述、优先级、预计耗时、开始时间、完成时间、状态、备注。

### 2.4 异常记录

遇到任何问题立即记录到进度管理.md 的异常表：

```
| 日期 | 异常 | 影响 | 处理 |
```

示例：
```
| 2026-07-13 | LLVM 重编译: make 卡死 + 链接 OOM | 无法生成 PTX |
  ✅ 根因: Debug+Static→OOM；方案: Release+Shared+Link_JOBS=1+Ninja |
```

## 三、技术决策流程

### 3.1 "讨论先于编码"原则

文档写完后、代码写之前，提出所有疑问。讨论结论写入 `项目设计.md`，包含：

- 问题背景
- 可选方案对比（用表格）
- 决策结果
- 决策理由
- 对后续任务的影响

### 3.2 方案对比方法

涉及到技术选型时，必须列对比表：

```
| 方案 | 可行性 | 优点 | 缺点 | 决策 |
|------|:---:|------|------|:---:|
| A    | ✅/❌/⚠️ | ... | ... |      |
| B    | ✅/❌/⚠️ | ... | ... | ✅   |
```

### 3.3 关键决策案例：放弃 MLIR GPU 路径

```
背景：Phase 3 完成了 MLIR GPU lowering (832 kernel)，想做性能 profiling

问题：NVPTX LLVM 后端缺失 → 需重编译 LLVM → Debug+Static 导致链接 OOM
      即使解决 OOM，832 kernel 全是 block=(1,1,1)，测得的是最差性能

方案对比：
  A. 坚持 MLIR 路径：先修 OOM → 加 tiling → 再 profiling
  B. 切换到 PyTorch 工具链：torch.profiler + nsys + Triton (全已就绪)

决策：B
理由: A 需要先做 tiling 才能看到有意义的 GPU 性能（因果倒置）
      B 的工具链全部在 RTX 4060 上验证通过，立即可用
      MLIR 后续作为对比维度加入，不丢弃

教训: 不要因为前面投入了很多就坚持错误的路径
      问自己"现在做什么能最快得到有效数据？"
```

## 四、Profiling 方法论

### 4.1 三层 Profiling 架构

不做 profiling 就优化是盲目的。三层架构从不同粒度给出数据：

```
Layer 1 (计算图):  torch.profiler  →  "哪个 aten op 最耗时？"
Layer 2 (GPU kernel): nsys / ncu   →  "kernel 是 compute-bound 还是 memory-bound？"
Layer 3 (图结构):     torch.fx      →  "哪里可以融合？计算图长什么样？"
```

### 4.2 对比表格驱动优化

Profiling 数据不是用来看的，是用来填表做决策的：

| 表 | 问题 | 驱动什么决策 |
|------|------|------|
| A: Op 耗时排名 | "时间花在哪了？" | 选哪个 op 做 Triton |
| B: Kernel 特征 | "瓶颈是什么？" | tiling vs 融合，哪个方向 |
| C: 子图结构 | "能融合吗？" | 哪些 op 链合为一个 kernel |
| D: 优化前后对比 | "快了多少？" | 这个优化是否值得保留 |
| E: 参数扫描 | "最佳配置？" | block size / tile 选择 |
| F: 端到端 | "整体快了多少？" | 叠加效果 |
| G: 汇总 | "学到了什么？" | 知识沉淀 |

### 4.3 三段式优化记录

每一项优化必须用三段式记录：

```
依据: 表A 显示 kernel X 占 XX% 总耗时，表B 显示它是 MEMORY-bound
动作: 写 Triton 融合 kernel，load→add→gelu 全在寄存器，省去中间 tensor
结果: 从 XXμs → YYμs (Z.Zx 加速)，端到端从 Ams → Bms
```

## 五、环境管理

### 5.1 Conda 隔离

```
所有 Python 工作在一个专用 conda 环境: novel_llm (Python 3.10.20)
所有脚本统一在脚本开头声明环境要求
CLAUDE.md 记录完整的环境依赖表
```

### 5.2 版本锁定

关键依赖必须固定版本：

| 组件 | 版本 | 为什么 |
|------|------|------|
| PyTorch | 2.12.0 | 最新 stable，torch.export API |
| transformers | 4.33.0 | 新版 (5.13) 引入 DynamicCache + aten.diff 导致导出失败 |
| torch-mlir | 20260531.828 | nightly wheel，预编译可用 |
| Triton | 3.7.0 | `tl.math.erf` 可用，`tl.math.tanh` → `tl.extra.cuda.libdevice.tanh` |

### 5.3 版本兼容性问题记录

| 问题 | 影响 | 处理 |
|------|------|------|
| transformers 5.13 GPT-2 导出失败 | DynamicCache 类型 + aten.diff 未注册 | 降级到 4.33.0 |
| pip 26.x 要求 Python 3.11+ | 无法安装 vLLM | 降级 pip<25 |
| IREE 20241104 不兼容 CUDA 13.0 | GPU 后端不可用 | CPU 用于功能验证，GPU 走纯 MLIR 路径 |

## 六、分支策略

### 6.1 按阶段建分支

```
main
  ├── phase3-linalg-gpu       (W9~W12: MLIR GPU lowering + 自定义 Pass)
  └── phase4-kernel-optimization  (W13~W15: PyTorch 工具链 Kernel 优化)
```

每个阶段从 main 开新分支。阶段内的所有 W 任务在同一个分支上迭代。

### 6.2 提交规范

```
格式:   <type>(W{n}): {中文描述}
类型:   feat: 功能开发
       docs: 文档更新
       fix:  问题修复
       refactor: 重构

示例:
  docs: Phase 4 W13 任务定义
  feat(W13): Profiling 完成 — 表A Op 耗时 + 表C 子图结构
  docs: 工作流新增讨论记录步骤 + FX图融合方案讨论

文档和代码分开提交（先 docs: 后 feat:）
```

## 七、关键教训

### 7.1 不要在阻塞路径上死磕

```
NVPTX OOM → 分析了三层根因 → 方案明确 (Release+Shared+Link_JOBS=1+Ninja)
但这需要 30-60 分钟编译 + 可能再失败

→ 问自己: "有没有其他方法今天就能得到同样的 profiling 数据？"
→ 答案: torch.profiler + nsys + Triton 全部已经就绪
→ 决策: 切换路径，NVPTX 作为后续参照

教训: 先拿到数据，再决定值不值得修路
```

### 7.2 Profiling 数据可能颠覆你的假设

```
假设: "GPT-2 有很多可以优化的 kernel"
实际: GEMM 占 75% GPU 时间，且 cuBLAS 已高度优化
      Triton 手写优化的端到端空间只有 ~5-10%

→ 这不会让 W14 失去价值
→ 价值从"追求大加速比"变成"建立 profiling→优化→验证的方法链路"
```

### 7.3 PyTorch Profiler API 因版本而异

```
torch.profiler 在不同 PyTorch 版本中属性名不同:
  旧: e.cuda_time_total
  新: e.self_device_time_total
  
→ 写 profiling 脚本时先验证 API，不要假设
→ 用 dir() 检查对象属性再写代码
```

### 7.4 文档质量决定项目能走多远

```
Phase 3 做了 4 个 W 任务 (W9~W12) 但文档更新滞后
→ 回头看时发现当时的很多细节已经忘了
→ Phase 4 严格执行"先写文档 → 再开发 → 再提交"

文档是给未来的自己的代码注释
```

### 7.5 先跑起来，再优化

```
不要试图一次写完"完美的 profiling 框架"
先用最简脚本跑出第一个数据点
有了数据，自然知道下一步需要什么

W13: 用 30 行脚本跑出 torch.profiler 的第一张表
→ 数据出来后再迭代脚本 (加参数、加输出格式、加可视化)
```

### 7.6 要度量某个优化，后端不能自带那个优化

```
想验证 tiling 的价值，先用 IREE 度量
→ 结果：预 tiling 后慢 9~1000x
→ 原因：IREE 自身就会 tiling/vectorize/并行化，
        喂它预 tiled IR 等于"打断它自己"，测到的是被打断的代价

→ 换 mlir-runner + --convert-linalg-to-loops（朴素循环）
→ 结果：tile 16~32 得 1.46x，K 不切反而 0.96x —— 这才有意义

教训: 选度量后端时先问一句"它会不会自己把这件事做了？"
```

### 7.7 因果顺序：tiling 是性能数据可解释的前提

```
Phase 3: GPU pipeline 无 tiling → 832 kernel 全 1 block × 1 thread
→ 此时测性能，测到的是"最差实现"的耗时，既无法做 roofline 判断，
  也掩蔽了其它优化的效果

教训: 不是"没 tiling 所以慢"，而是"没 tiling，测出来的数没有分析价值"
      先让被测对象成为一个"合理实现"，再谈优化效果
```

### 7.8 op 语义从源码确认，别靠印象

```
多次需要确认 transform op 的语法与支持范围
→ 与其猜，不如直接读定义文件：mlir/include/mlir/Dialect/*/TransformOps/*.td

例：tile_reduction_using_forall 不支持 matmul（只支持纯归约 op）、
    map_nested_forall_to_threads 要求 gpu.launch + bufferized forall + mapping 属性
    —— 这些结论全部来自 .td，不是猜的

教训: 本版本"没有缺 op"，只有"没查"；.td 是一手依据，查它比自己试快
```

## 八、文件组织约定

```
项目根目录
├── work/           ← 所有文档（不以代码形式存在）
│   ├── 项目设计.md
│   ├── 工作划分.md
│   ├── 进度管理.md
│   ├── 开发经验.md    ← 本文档
│   ├── archive/       ← 已完成阶段的归档
│   └── task/          ← 专项讨论 / 深层分析
├── scripts/         ← Python 脚本（可执行）
├── tools/           ← Shell 脚本（可执行）
├── triton/          ← Triton kernel
├── benchmarks/      ← profiling 数据和结果
│   ├── tables/      ← CSV 对比表格
│   ├── results/     ← 原始 profiling 数据
│   └── analysis/    ← 分析报告
├── models/          ← 模型定义
├── mlir/            ← MLIR IR 文件
└── passes/          ← 自定义 MLIR Pass (Phase 3)
```

命名规则：
- 脚本文件：`动词_名词.py`（如 `profile_gpt2_torch.py`, `extract_gpt2_graph.py`）
- 表格文件：`table_字母_英文描述.csv`（如 `table_a_op_timing.csv`）
- 任务文档：`讨论-主题.md` / `分析-主题.md`（如 `分析-NVPTX_LLVM编译OOM.md`）

## 九、从零开始的推荐顺序

如果这是一个新项目，推荐的启动顺序：

```
Week 1:
  ├── 初始化 CLAUDE.md（环境、项目结构、工作流）
  ├── 创建 work/ 三份文档骨架
  ├── 定义 W0~W1 任务（环境确认 + 验证）
  └── 跑通最小验证链路（一个简单模型从头到尾）

Week 2+:
  ├── 定义每一周的 W 任务（先写文档！）
  ├── 每个 W 完成后立即 commit
  ├── 遇到异常立即记录
  └── 每个阶段结束时写总结报告 → archive/

日常:
  ├── 开始工作 → 读进度管理.md 当前状态
  ├── 有新发现 → 追加到项目设计.md 关键发现
  ├── 有决策讨论 → 写入项目设计.md 对应章节
  └── 完成任务 → 更新进度管理.md + commit
```
