# Phase 5: 回到 Tiling — 补齐 Phase 3 遗留链路 (2026-09-13+)

> **背景**：Phase 3 的 GPU 通道因"无 tiling → 832 kernel 全 1 block × 1 thread"失去分析价值，当时选择绕开（转 Phase 4）。
> 现回头补齐 —— 因为 **tiling 是让性能数据可解释的前提**：没有 tiling，测到的是"最差实现"的耗时，
> 无法做 roofline 判断，也掩蔽了其它优化的效果。
>
> 详细分析见 `work/task/分析-Tiling概念与算子验证进度.md`。

## W16：Tiling 验证与 CPU 度量框架 ✅ (已完成 2026-09-13)

- **描述**：
  1. ✅ 概念澄清：Tiling / Layout / Mapping 三者区分；**Tiling ≠ 只切 K 维**
  2. ✅ 核查进度：算子链路（W4~W9）**未到 tiling**；GPU pipeline 只做了 Mapping 未做 Tiling
  3. ✅ L1 结构验证：transform dialect tiling 链路可用（`tile_using_for` / `tile_using_forall`）
  4. ✅ L2 语义验证：5 个变体数值与 numpy 一致
  5. ✅ L3 映射结构：`forall` 可映射，但**加串行 K 循环后退回 `(1,1,1)`**
  6. ✅ K 维 tiling 配方：`forall[32,32]` + `for[0,0,16]`（`tile_reduction_using_forall` **不支持 matmul**）
  7. ✅ CPU 度量框架：`scripts/verify_tiling.py`（runner / iree 双后端 + tile 扫描）
  8. ✅ 首版正面数据：tile 16~32 最优（**1.46x**），**K 不切反而倒退**（0.96x）
- **输入**：`mlir/handwritten/tile_matmul_transform.mlir`、mlir-opt(23.0.0git)、mlir-runner
- **产出**：
  - `scripts/verify_tiling.py`
  - `benchmarks/tables/table_h_tiling_runner.csv`、`benchmarks/tables/table_h_tiling_cpu.csv`
  - `work/task/分析-Tiling概念与算子验证进度.md`
- **关键发现**：
  - **IREE 不适合作 tiling 的度量后端** —— 它自身会 tiling/vectorize/并行化，喂预 tiled IR 等于打断它自己，测得的是"被打断的代价"（慢 9~1000x）
  - 度量后端必须"**不做 tiling**"，故选 `mlir-runner` + `--convert-linalg-to-loops`（朴素循环）
  - `tile_using_for` 在张量层引入 `insert_slice` → bufferize 后是 `memref.copy`，即**朴素路径下 tiling 会引入真实数据搬运**（也是 promotion 的落点）
  - `scf.forall`（张量上的 forall + `parallel_insert_slice`）会让 IREE **段错误**（`Value::getParentBlock`）
- **难点**：CPU 只能验证"数值 + 缓存复用"两条轴；shared memory / occupancy 无法验证
- **风险**：GPU 性能轴仍需 NVPTX（未通）；__高__
- **优先级**：P0（阻塞"MLIR 能否加速"这一结论）
