## 二、五个可切入的业内方向

### 方向一：算子融合的「自动决策」——为什么该融合、融合收益多少

**业内痛点**：TVM/XLA/MLIR 都在做自动融合，但**决策规则是拍脑袋的**。什么 pattern 该融合、融合后收益多少，缺少量化依据。很多融合反而变慢（项目 W5 就发现了 `linalg-generalize-named-ops` 有反效果，小模型 +6.3%）。

**项目积累可直接复用**：
- `analyze_dataflow.py` 已能识别「可融合链」+「融合冲突点」
- `annotate_graph_perf.py` 已能给出「融合前每个 op 的耗时+显存」

**能做什么**：给每个融合候选自动算「融合前总耗时 vs 融合后预估耗时」，产出一张**融合收益排序表**——这正是编译器融合决策引擎缺的东西。项目里 GELU 融合的「8 kernel → 1 kernel，省 7 个中间 tensor」就是这个方法论的雏形。

**新工作量**：低。工具几乎现成。

---

### 方向二：KV Cache 显存爆炸的可视化与定量分析

**业内痛点**：长序列推理（128K context）下 KV Cache 显存爆炸，是 LLM 服务的头号成本。vLLM 的 PagedAttention、量化 KV Cache 都在解决这个。

**项目积累可直接复用**：`annotate_graph_perf.py` 已有 `memory_mb` 维度，能标注每个 op 的显存占用。

**能做什么**：把 KV Cache 的显存增长路径可视化——从 token 序列长度 → attention 层数 → KV Cache 大小的定量映射。回答「128K context 到底吃多少显存、吃在哪一层」，这是量化 KV Cache 优化收益的前提。

**新工作量**：中。直接延伸 annotate 的 memory 维度。

---

### 方向三：编译器生成 kernel vs 手写 kernel 的「差距量化」

**业内痛点**：MLIR/Triton 社区长期争论「编译器自动生成的 kernel 能不能赶上手写」。但缺乏同模型的公平对比数据。

**项目积累可直接复用**：Phase 4 计划里明确留了这个「对比维度」——MLIR 自动 lowering 的 832 kernel vs 手写 Triton 融合 kernel。NVPTX 阻塞已分析清楚（Release+Shared+Link_JOBS=1+Ninja 可解，见 `分析-NVPTX_LLVM编译OOM.md`）。

**能做什么**：同一个 GPT-2，三条路径（cuBLAS 基线 / MLIR 自动 lowering / 手写 Triton）的耗时+显存三方对比。这是业内很想要、但很少人做的公平基准数据。

**新工作量**：高。需先解决 NVPTX 重建。

---

### 方向四：动态 shape / 动态控制流的编译分析

**业内痛点**：LLM 推理的 batch size、序列长度都是动态的，而编译器优化大多假设静态 shape。动态 shape 下的融合、tiling 决策是公认难题。

**项目积累可直接复用**：W9 的 GPT-2 动态导出（符号维度 2032 处）已踩过这个坑，项目设计里记录了「动态导出的价值在符号维度 ?，不在循环」的认知。

**能做什么**：用 `analyze_dataflow.py` 分析动态 shape 下哪些融合是安全的（shape 无关的），哪些必须静态 shape 才能做。这个「动态 shape 融合安全性分析」是 torch.compile 生态在解决的问题。

**新工作量**：中。有 W9 积累。

---

### 方向五：多架构泛化验证（GQA / RoPE / MoE / SwiGLU）

**业内痛点**：优化方法在 GPT-2（MHA + GELU）上有效，但 Qwen/Llama 用的是 GQA + RoPE + SwiGLU + MoE，结构完全不同。优化方法能否泛化是未知数。

**项目积累可直接复用**：`mlir/models/{qwen,llama,bert}/` 目录已留好，`analyze_dataflow.py` 和 `annotate_graph_perf.py` 都是模型无关的（只依赖 torch.export）。

**能做什么**：同一套工具跑 Qwen2-1.5B / Llama-3.2-1B，对比 GQA vs MHA 的 attention 数据流差异、SwiGLU vs GELU 的融合机会差异——产出一份「架构差异如何影响优化策略」的分析。

**新工作量**：低。工具直接可复用。

## 三、优先级建议

| 方向 | 贴合度 | 复用度 | 新工作量 | 建议 |
|------|:---:|:---:|:---:|:---:|
| 一、融合自动决策 | ⭐⭐⭐ | ⭐⭐⭐ | 低 | **最推荐**，工具几乎现成 |
| 二、KV Cache 显存 | ⭐⭐⭐ | ⭐⭐ | 中 | 直接延伸 memory 维度 |
| 三、编译器 vs 手写 | ⭐⭐ | ⭐⭐ | 高（需 NVPTX） | 价值高但门槛高 |
| 四、动态 shape | ⭐⭐ | ⭐⭐ | 中 | 有 W9 积累 |
| 五、多架构泛化 | ⭐⭐⭐ | ⭐⭐⭐ | 低 | 工具直接可复用 |

**结论**：方向一（融合自动决策）和方向五（多架构泛化）投入产出比最高——工具几乎现成，直接换数据源就能出成果。
